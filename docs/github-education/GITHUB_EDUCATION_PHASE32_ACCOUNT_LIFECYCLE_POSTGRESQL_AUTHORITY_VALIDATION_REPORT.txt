PHASE 32 AUTHORITY SOURCE-OF-TRUTH + ADMIN ROUTE HOTFIX
==========================================================
Date: 2026-08-11

Root cause A - user/admin diagnostics split-brain
------------------------------------------------
- /health correctly derived Phase 32 authority from FIRESTORE_ACCOUNT_LIFECYCLE_COMPATIBILITY_DISABLED.
- accountLifecycleService previously did not receive or enforce that flag, so PostgreSQL signup/terms endpoints could still run while /health said authority disabled.
- user signup/terms/compliance observations also hardcoded backendApplied=true and PostgreSQL sources instead of deriving them from the backend compatibility payload.
- This made "user backend applied=yes" compatible with "administrator backend applied=no" and therefore the user-side value was not proof of backend authority.

Source fix A
------------
- accountLifecycleService now accepts authorityEnabled and rejects all Phase 32 lifecycle methods with account_lifecycle_authority_disabled / HTTP 503 when false.
- server/src/index.mjs wires authorityEnabled from config.accountLifecycleCompatibilityDisabled.
- frontend accountLifecycleAuthority exports a compatibility-payload parser shared by health and operation observations.
- signup/terms/compliance successful observations derive authority fields from the actual API compatibility payload.
- failed operations no longer overwrite backendApplied/source fields with hardcoded PostgreSQL success values.

Root cause B - administrator route could be overwritten
-------------------------------------------------------
- persistent administrator route intent existed, but multiple independent user-route writers could still call pushAppPath/replaceAppPath and set user view during asynchronous auth/member/terms transitions.
- the administrator controller later attempted to restore /admin, leaving a race and visible regression opportunity.

Source fix B
------------
- appRoutes now rejects user pathname writes while mk_laptop_admin_route_intent is active and preserves /admin.
- useAppNavigationController blocks implicit user-tab navigation while the intent is active.
- popstate cannot switch an active administrator intent to a user route.
- explicit administrator-to-user navigation clears the intent before user navigation.
- administrator authentication invalidation paths explicitly clear the intent and route guard.

PHASE 32 NEW-SIGNUP POSTGRESQL RUNTIME READ-MODEL HOTFIX
========================================================
Date: 2026-08-11

Actual Staging finding after source-of-truth hotfix
---------------------------------------------------
Phase 32 diagnostics are now correct in the tested user path:
- Account lifecycle authority requested: yes
- Account lifecycle backend applied: yes
- Signup profile source: postgresql
- Signup Firestore bootstrap: retired
- Terms consent source: postgresql
- Account recovery source: postgresql
- Phase 32 authority error: -

However, a newly registered user that was approved by an administrator failed immediately after login with:
- rental restriction PostgreSQL read unavailable while legacy Firestore fallback is disabled;
- member profile PostgreSQL read unavailable while legacy Firestore fallback is disabled.

Root cause
----------
Phase 32 signup correctly creates the canonical member in app_member_accounts and retires Firestore signup bootstrap.
The existing user runtime reads still consume the PostgreSQL read-model tables introduced in earlier phases:
- app_user_member_shadows for /api/users/me/member-profile-candidate;
- app_user_rental_restriction_shadows for /api/legacy/rental-restriction-candidate.

Legacy users already had those rows because earlier Firestore bootstrap/synchronization paths created them. A Phase 32 PostgreSQL-only signup intentionally creates no Firestore userAccounts/rentalRestrictions documents, so no legacy bootstrap path exists to create the two PostgreSQL read-model rows. The result was a 404 candidate read with Firestore fallback correctly blocked by Phase 27.

Source fix
----------
server/src/auth/user-clerk-auth-repository.mjs now materializes the required PostgreSQL runtime read models when:
1. a Phase 32 signup is linked to its Clerk/app_user_id during provision; and
2. an existing already-provisioned Phase 32 signup completes a verified Clerk login.

The second path is a self-heal for accounts created before this hotfix.

Safety boundary
---------------
The materialization is restricted to accounts satisfying both:
- lifecycle_authority_mode='postgresql-authoritative';
- terms_consent_bootstrap_completed_at IS NOT NULL.

This targets Phase 32 PostgreSQL account-lifecycle accounts and avoids converting arbitrary legacy members into default no-restriction accounts.

Member read model:
- source_collection = app_member_accounts;
- authority_mode = postgresql-authoritative;
- mirror_state = retired;
- current profile/status/identity/terms fields are copied from canonical app_member_accounts.

Rental restriction read model:
- a missing row for an eligible Phase 32 signup is initialized as restriction_exists=false;
- authority_mode = postgresql-authoritative;
- mirror_state = retired;
- an existing restriction_exists=true row is never overwritten;
- existing legacy/member restriction data is therefore not reset to an unrestricted state.

No Firestore re-enable
----------------------
This hotfix does not restore Firestore signup bootstrap, member profile fallback, or rental restriction fallback. It creates/repairs the required PostgreSQL read models from the PostgreSQL canonical account only.
