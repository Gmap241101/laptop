PHASE 32 APPROVAL STATUS + AUTHORITATIVE RENTAL READ HOTFIX
=========================================================
Date: 2026-08-11

Actual Staging findings after the new-signup read-model hotfix
-------------------------------------------------------------
1. Existing converted accounts can sign in, but the user rental-history screen reports that PostgreSQL rental requests are unavailable while legacy Firestore fallback is disabled.
2. Brand-new Phase 32 accounts can initially authenticate, but after an administrator changes the member status from pending to active, a subsequent login briefly succeeds and is immediately signed out.

Root cause A - stale Firestore approval status during Clerk-authoritative login
-------------------------------------------------------------------------------
Phase 30 retired the Firestore member-status write mirror. Administrator approval therefore changes app_member_accounts.status in PostgreSQL but intentionally leaves the compatibility Firestore userAccounts.status unchanged.

useUserLoginController finalized an otherwise successful Clerk login by rereading Firestore userAccounts and using that stale status as the session authorization decision. A newly approved account could therefore have:
- PostgreSQL / Clerk session memberStatus = active;
- Firestore compatibility status = pending.

The finalizer interpreted the stale pending value as inactive and immediately signed out both Clerk and Firebase compatibility sessions.

Fix:
- Clerk session userAuthentication.memberStatus is now passed into finalizeUserAuthentication.
- When the Phase 23/32 Clerk user-auth cutover is requested and a PostgreSQL memberStatus is present, that authoritative status is used for active/pending/blocked/retired login decisions.
- Firestore userAccounts remains available only for compatibility profile/directory fields still needed by the transitional flow; it no longer overrides PostgreSQL approval status.
- Client Trust verification and ordinary password login use the same authoritative member-status contract.

Root cause B - authoritative rental read retained a legacy member-shadow gate
-----------------------------------------------------------------------------
Phase 29 rental-request reads already use canonical app_rental_requests when the rental write mirror retirement flag is active. However createRentalRequestService.getCurrent()/syncCurrent() still entered context() that always required app_user_member_shadows before reaching the canonical query.

That legacy shadow is not required to identify or query a Clerk-authenticated user's canonical PostgreSQL rental requests. Converted accounts with an incomplete/retired legacy member-shadow state could therefore receive member_shadow_not_found before app_rental_requests was queried. With Phase 27 Firestore fallback disabled, the frontend correctly surfaced this as PostgreSQL rental-history unavailable.

Fix:
- PostgreSQL authoritative rental get/sync paths now require the application user and Firebase identity link, but do not require app_user_member_shadows.
- Legacy member-shadow validation remains in place only for legacy Firestore source/sync/compare paths where previousAccountUids/email are actually needed.
- No Firestore rental read fallback or shadow resynchronization was re-enabled.

- Phase 23 frontend user-Clerk lifecycle smoke asserts that PostgreSQL/Clerk memberStatus is wired into final login authorization and takes precedence over stale compatibility Firestore status.

PHASE 32 POSTGRESQL SESSION GATE / FIRESTORE STATUS BYPASS HOTFIX
===============================================================
Date: 2026-08-11
Runtime revision: phase32-canonical-member-profile-read-20260811-2054

Actual Staging finding after approval-status/rental-read hotfix
-------------------------------------------------------------
The user redeployed both Heroku Staging and Vercel Staging, but the two reported symptoms remained unchanged:
1. an existing converted account still received the generic PostgreSQL My Rental Requests failure while legacy Firestore fallback was disabled;
2. a brand-new account approved by an administrator still briefly signed in and then lost the user session.

The public Heroku root response confirmed that the deployed service was Phase 32 and the expected PostgreSQL/retirement flags were active. Therefore this revision treats the failure as an execution-path problem rather than a failed deployment or disabled feature flag.

Root cause A - PostgreSQL status was still followed by mandatory Firestore account finalization
----------------------------------------------------------------------------------------------
The previous hotfix passed PostgreSQL memberStatus into finalizeUserAuthentication, but finalizeUserAuthentication still always fetched Firestore userAccounts and retained the legacy directory/status verification branch. Phase 30 intentionally retired the Firestore member-status mirror, and Phase 32 intentionally retired Firestore signup bootstrap. Therefore a newly approved PostgreSQL account can legitimately have stale `pending` compatibility status or no Phase 32 Firestore signup account row suitable for authorization.

A successful Clerk/PostgreSQL session could consequently be followed by a legacy Firestore decision and then immediate sign-out.

Fix:
- the user session response now supplies both the per-user PostgreSQL memberStatus and the backend member-status/profile source contract to login finalization;
- when Clerk user authority is requested and both member status/profile sources are PostgreSQL, login finalization treats PostgreSQL memberStatus as authoritative and completely skips Firestore userAccounts approval/directory-status re-evaluation;
- the compatibility Firestore finalization path remains only for rollback/non-cutover sessions;
- ordinary password login and Clerk Client Trust completion use the same source-of-truth gate.

Root cause B - post-login membership watcher could still sign out from a stale profile state
------------------------------------------------------------------------------------------
After login finalization, useUserMembershipStatusController watches userProfile.status. During transitional refresh, that profile can still temporarily contain a stale pending/blocked/retired status. Previously the watcher immediately cleared the local user session and Firebase compatibility session from that value.

Fix:
- the inactive-member watcher now waits until the local authenticated user session is actually established;
- before any inactive-status logout in Clerk-authoritative mode, it calls `/api/users/auth/session` and confirms the canonical PostgreSQL memberStatus;
- PostgreSQL active/profileRequired overrides a stale local profile and suppresses false logout;
- a genuinely inactive PostgreSQL status still clears the local session and signs out both Clerk and Firebase compatibility sessions;
- if canonical PostgreSQL status cannot be verified, the watcher does not destroy an otherwise established session from a stale local value; it surfaces an error for diagnosis instead.

Root cause C - My Rental Requests could start before Clerk/local user session establishment
------------------------------------------------------------------------------------------
The rental subscription controller was triggered by Firebase Auth and member-profile readiness. Firebase compatibility login completes earlier than Clerk session establishment in the Phase 23/32 flow. The PostgreSQL rental API client requires a Clerk bearer token, so My Rental Requests could call `getRentalRequestReadCandidate()` during the short interval where Firebase/profile were ready but `clerk.session` / local user auth session was not yet established. This produced the same generic PostgreSQL-unavailable toast and did not necessarily retry when the Clerk session later became ready.

Fix:
- the rental read controller now receives `userAuthSessionUid`;
- in Clerk-authoritative mode it does not initiate a PostgreSQL rental read until `userAuthSessionUid === firebaseAuthUser.uid`;
- `userAuthSessionUid` is an effect dependency, so the authoritative read automatically retries when login finalization establishes the local session;
- no Firestore fallback or legacy rental shadow synchronization is re-enabled.

PHASE 32 NATIVE-MEMBER RUNTIME AUTHORITY HOTFIX
================================================
Date: 2026-08-11
Runtime revision: phase32-new-member-runtime-authority-20260811-2108

Actual Staging findings
-----------------------
After prior Phase 32 fixes, login and canonical profile display were healthy, but PostgreSQL-only native signup accounts still exposed two legacy-runtime failures:
1. rental application could execute a Firestore latest-overdue/restriction preflight and abort when Firestore data/permission was unavailable;
2. member withdrawal / role resolution could require Firestore `userAccounts/{uid}` and `adminAccounts/{uid}` access even though the native account lifecycle bootstrap had intentionally retired those Firestore dependencies.

Structural root cause
---------------------
Phase 32 account lifecycle authority and older per-domain cutovers were independently latched in query/session state. A native account could therefore be created with PostgreSQL-only signup authority while a fresh tab/session later resolved rental/member/user-lifecycle behavior back to a legacy Firestore code path. That state is not a valid authority combination.

Runtime authority fix
