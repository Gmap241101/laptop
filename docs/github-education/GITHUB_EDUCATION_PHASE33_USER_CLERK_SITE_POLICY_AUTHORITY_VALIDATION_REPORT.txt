2. Successful administrator domain sync publishes rental:site-content-invalidated and a localStorage broadcast so same-tab and other same-origin tabs discard stale content immediately.
3. User home, popup/footer and site-settings controllers subscribe to the invalidation and automatically re-read PostgreSQL on invalidation, window focus, pageshow, and return-to-visible events.
4. Administrator full-repair session key is bumped to mk_phase33_public_content_authority_repair_20260812_0045 so the current Firestore -> PostgreSQL reconciliation runs again after deployment without manual diagnostics buttons.
5. Site-content sync now compares canonical document key + payload + enabled + sortOrder + sourceUpdatedAt after PostgreSQL write-back. A mismatch fails with site_content_sync_payload_mismatch rather than incorrectly reporting synced.
6. Frontend hotfix revision is phase33-public-content-cache-invalidation-hotfix-20260812-0045.

Observed Staging regression:
- Administrator Firestore-backed banner/content lists remained populated.
- Public PostgreSQL reads still showed an incomplete visual set (for example only one quick-link banner).
- Saving a main visual could commit to Firestore and then fail during PostgreSQL synchronization with `unauthorized`.
- Repeated diagnostics synchronization buttons did not produce a durable fix.

Historical recurrence and confirmed boundary:
- The same class of defect first appeared during Phase 25: PostgreSQL `home` contained only a partial document set while Firestore held the full home visual configuration.
- The Phase 25 hotfix moved browser bootstrap source reads to `getDocFromServer()` / `getDocsFromServer()` so cached Firestore snapshots could not seed an incomplete PostgreSQL copy.
- Phase 33 still retained a browser-mediated bridge: after a Firestore administrator mutation, the browser read the full Firestore domain and uploaded that snapshot to `/api/admin/site-content/:domain/sync`.
- A Clerk bearer failure after the Firestore commit therefore left Firestore newer than PostgreSQL. That split-brain explains both the `unauthorized` save error and a public user page that continues to show only the older partial PostgreSQL set.
- The browser remained an unnecessary completeness/authentication boundary even after the Phase 25 server-snapshot fix.

1. Add `server/src/firestore/firestore-site-content.mjs`.
2. The backend sync route now ignores browser document payloads and reads the entire requested Firestore domain itself via Firestore REST using the verified administrator Firebase ID token.

4. The backend replaces the PostgreSQL domain transactionally from that server-source snapshot and returns `siteContentSource.mode=firestore-server-backend-full-domain` plus the full source document count.
5. Frontend write-through accepts success only when the backend confirms this full-server-source mode and the PostgreSQL persisted count equals the Firestore server count.
6. The frontend no longer reads Firestore documents/collections as the PostgreSQL replacement payload during site/policy synchronization.
7. If the backend returns Clerk `401 unauthorized`, the frontend forces a fresh Clerk session JWT with `session.getToken({ skipCache: true })` and retries once. If Firebase authentication is the rejected credential, it forces a fresh Firebase ID token and retries once.
8. Administrator auto-repair session key is bumped to `mk_phase33_public_content_authority_repair_20260812_0117`, so the complete backend-source reconciliation runs again after this deployment without any diagnostics-button action.

10. Backend root exposes `publicContentSyncRevision=phase33-public-content-full-server-sync-hotfix-20260812-0117`.
